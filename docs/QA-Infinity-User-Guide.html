QA Infinity User Guide

A self-hosted, AI-driven QA automation platform that generates test cases from natural language inputs, auto-writes Robot Framework scripts, runs them in a managed browser cluster, and self-heals broken selectors — all from a single Docker Compose stack.

✍️
AI Test Writer
Generate full test cases from URLs, API specs, Jira stories, PDFs, screenshots, or existing TC patterns.
📜
Script Generation
Automatically produces Robot Framework scripts with locked locators and trace-verified selector hints.
▶️
Managed Execution
Runs scripts in a headless Playwright cluster. Watch live via built-in noVNC browser.
🩹
Self-Healing
Detects broken selectors and proposes AI-generated fixes without re-running the entire suite.
🎯
Skills System
Teach the AI how to log in, navigate menus, and fill forms — reusable across all generated scripts.
💬
AI Chat
Ask questions about your test suite, generate ad-hoc tests, or get explanations via project-aware chat.
📁
SharePoint — releases, supporting docs & more. Beyond this repository, the QA Infinity project folder on SharePoint holds release builds (releases/Fresh Install, releases/hotfix), supporting documentation, and other project files: QA Infinity on SharePoint.

🏗️ Fresh Server Setup (RHEL / CentOS)

For standing up QA Infinity on a brand-new server that has internet access. If it doesn’t, use Air-Gapped Deployment instead — that path builds images elsewhere and ships tarballs over.

Check what you’re actually working with

Don’t trust the hostname or what you were told the OS is — check directly:

cat /etc/os-release          # e.g. "CentOS Stream 9" on a box named like a RHEL prod server
whoami
sudo firewall-cmd --state    # running / not running
getenforce                   # Enforcing / Permissive / Disabled
df -h                        # partition layout — matters a lot belowbash
💡
If firewalld isn’t running and SELinux is Disabled, that’s two whole categories of setup work (port rules, SELinux relabeling of bind mounts) you get to skip. Don’t add them speculatively — verify first.

Install Docker Engine + Compose v2

sudo dnf install -y dnf-plugins-core
sudo dnf config-manager --add-repo https://download.docker.com/linux/rhel/docker-ce.repo
sudo dnf install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-pluginbash

If this fails with conflicts against podman/runc/containerd (RHEL/CentOS ship Podman by default, and podman-docker collides with docker-ce), rerun with --allowerasing.

sudo systemctl enable --now docker
sudo usermod -aG docker <your-user>
newgrp docker            # or log out/in
docker compose version   # confirm v2bash
ℹ️
sudo dnf install may print “Unable to read consumer identity” / “not registered with an entitlement server” — that’s just RHEL’s subscription-manager nagging because the box isn’t registered with Red Hat. Harmless on CentOS Stream, ignore it.

Fix disk layout before building anything

⚠️
This is the step that will bite you if skipped. Servers are often provisioned with a small OS disk (/, /var, a few GB each) and a large separate data volume (/data, /opt). Docker and containerd both default to storing everything under /var/lib/..., which fills up mid-build with a cryptic error, not an obvious “disk full” message: failed to compute cache key: symlink ... /var/lib/containerd/...: no space left on device

Check first with df -h. If /var is small and something else (e.g. /data) has real space, redirect both Docker’s data-root and containerd’s root/state before running any build — both daemons need a full stop/reconfigure/restart cycle, which is disruptive once containers are running.

Redirect Docker’s data-root:

sudo systemctl stop docker
sudo mkdir -p /data/docker
sudo tee /etc/docker/daemon.json <<'EOF'
{
  "data-root": "/data/docker"
}
EOF
sudo rm -rf /var/lib/docker/*   # safe pre-first-build; it's only cache at this point
sudo systemctl start docker
docker info | grep "Docker Root Dir"   # should show /data/dockerbash

Redirect containerd’s root/state — separately, it’s a different daemon:

docker-ce on RHEL/CentOS installs containerd.io as its own systemd service with its own config, independent of Docker’s daemon.json. Fixing Docker’s data-root alone is not enough:

sudo systemctl stop docker containerd
sudo mkdir -p /data/containerd /data/containerd-state
sudo containerd config default | sudo tee /etc/containerd/config.toml > /dev/null
sudo sed -i 's|^root = .*|root = "/data/containerd"|' /etc/containerd/config.toml
sudo sed -i 's|^state = .*|state = "/data/containerd-state"|' /etc/containerd/config.toml
sudo rm -rf /var/lib/containerd/*
sudo systemctl start containerd docker
grep -E '^root|^state' /etc/containerd/config.toml   # confirm the paths took
df -h /var /data                                       # confirm /var is no longer filling upbash

Do both together, in that order, before the first build attempt.

SELinux & firewalld only if step 1 showed them active

Skip this whole section if getenforce said Disabled and firewall-cmd --state said not running.

If SELinux is Enforcing: docker-compose.yml bind-mounts host paths (./scripts:/scripts, ./nginx/nginx.conf:...) that need container-accessible labels or the containers get silent permission-denied errors:

sudo dnf install -y policycoreutils-python-utils   # provides semanage, if missing
sudo semanage fcontext -a -t container_file_t "/data/qa-infinity/scripts(/.*)?"
sudo semanage fcontext -a -t container_file_t "/data/qa-infinity/nginx(/.*)?"
sudo restorecon -Rv /data/qa-infinity/scripts /data/qa-infinity/nginxbash

If firewalld is running: open the app ports — skip 5655 (Prisma Studio, dev-only, don’t expose it):

sudo firewall-cmd --permanent --add-port=3100/tcp   # UI
sudo firewall-cmd --permanent --add-port=4100/tcp   # API
sudo firewall-cmd --permanent --add-port=6180/tcp   # noVNC live runner view
sudo firewall-cmd --reloadbash
ℹ️
Even with the local firewall off/disabled, there may still be a network-level firewall or security group in front of the box that needs these same three ports opened separately — that’s outside anything you can check from the server itself.

Get the code onto the server

Check target directory ownership before cloning into it — a data volume is often root-owned even when your user has sudo:

sudo dnf install -y git   # not installed by default on a minimal image
ls -ld /databash

If it’s root:root with no group/other write bit, git clone into it fails with Permission denied. Fix by owning the specific subdirectory (don’t chown the whole /data mount — other things may live there):

sudo mkdir -p /data/qa-infinity
sudo chown -R <your-user>:<your-user> /data/qa-infinity
git clone https://github.com/albinbenny-dev/qa-infinity.git /data/qa-infinity
cd /data/qa-infinitybash

Configure & start

See Configure above for the full .env reference. Two fields need special attention on a fresh server: if you’re copying an existing .env from another server (valid — DB password, JWT secret, LLM/JIRA/SMTP config all carry over fine), update these to match the new server or you’ll get CORS errors and broken report/email links pointing at the old box:

ip -4 addr show scope global | grep inet   # get this server's IPbash
CORS_ORIGIN=http://<new-server-ip>:3100
APP_URL=http://<new-server-ip>:3100.env

Also check docker-compose.yml — qa-api/qa-runner have an extra_hosts entry hardcoding an internal hostname to an IP. Only matters if this server needs to reach that host for test execution against an internal target app; harmless otherwise.

chmod +x start.sh
./start.sh --buildbash

First build takes ~3–5 minutes. If this fails with no space left on device, you skipped the disk-layout step above — go back and do it before retrying; a partial build’s cache doesn’t carry over cleanly between data roots.

Verify

docker compose ps                                   # all 5 containers healthy
curl -sf http://localhost:4100/health && echo OKbash

Then open http://<server-ip>:3100, register the first account (auto-gets Super Admin), create a project, and confirm a test run executes end-to-end (watch it live via noVNC at http://<server-ip>:6180).

💡
Quick reference — the two things that most often go wrong: (1) /var is a small partition; Docker and containerd both default there — fix both daemon.json and /etc/containerd/config.toml, they’re separate daemons. (2) /data is root-owned; git clone into it fails silently-ish with Permission denied — chown the specific subdirectory, not the whole mount.

⎈️ Kubernetes / OpenShift Production

Lessons learned bringing QA Infinity up in restricted, on-premises Kubernetes / OpenShift environments.

Pod Security Context

QA Infinity images are built to run as non-root. Apply this security context to every workload in your Helm chart or Kubernetes manifests:

securityContext:
  runAsNonRoot: true
  runAsUser: 1000          # 'node' user (api), 'runner' user (runner)
  fsGroup: 1000
  supplementalGroups: [0]
  seccompProfile:
    type: RuntimeDefault
  capabilities:
    drop: [ALL]yaml

For the UI (qa-ui / nginx), use runAsUser: 65534 (nobody).

ImageRuntime user
qa-apinode (uid 1000, built into node:alpine)
qa-runnerrunner (uid 1000, created in Dockerfile)
qa-uinobody (uid 65534, built into nginx:alpine)

qa-postgrespostgres (uid 999, official image default)

Postgres on NFS / Restricted Volumes

The stock postgres:16-alpine image runs initdb as the postgres user (uid 999). On NFS-backed PVCs the volume root is usually owned by root, so initdb fails with permission errors unless the runtime UID owns the data directory.

Fix: set PGDATA to a subdirectory of the mount point. Postgres will mkdir and chown the subdirectory at init time, and because the runtime UID owns the subdirectory (not the volume root) the permission check passes.

environment:
  - PGDATA=/var/lib/postgresql/data/pgdata   # ← subdirectory, not the volume root
volumes:
  - qa-pgdata:/var/lib/postgresql/data       # ← PVC mounted at parent diryaml
⚠️
Existing deployments: changing PGDATA on a deployment that already has data in /var/lib/postgresql/data will cause Postgres to reinitialise from scratch. Take a pg_dump backup before applying this to an existing cluster, then restore after.

Redis — Non-Root Configuration

The default Redis config writes its RDB snapshot to /data (the volume mount root), which is root-owned on most restricted PVCs. With stop-writes-on-bgsave-error yes (the Redis default), a failed background save blocks all writes while Redis keeps responding to PING — the pod looks healthy but all operations return errors.

docker-compose.yml already passes the correct flags (redis-server --dir /tmp --stop-writes-on-bgsave-error no). For Helm / Kubernetes, set these in your Redis config map or command args:

command: ["redis-server"]
args:
  - "--dir"
  - "/tmp"
  - "--stop-writes-on-bgsave-error"
  - "no"
  - "--requirepass"
  - "$(REDIS_PASSWORD)"yaml

WebSocket Proxying (Contour / Envoy)

The live execution log streams over Socket.io (WebSocket upgrade). OpenShift’s HAProxy router proxies WebSocket upgrades automatically; Contour/Envoy does not — you must opt in per-route. Add this annotation to the qa-ui Ingress:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: qa-infinity
  annotations:
    projectcontour.io/websocket-routes: "/"   # ← enables WS upgrade on all paths
spec:
  rules:
    - host: qa-infinity.apps.your-cluster.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: qa-ui
                port:
                  number: 8080yaml
⚠️
Without this annotation the Socket.io handshake falls back to HTTP long-polling, which causes the live log panel to appear blank even though tests are running.

TLS / Ingress Configuration

QA Infinity must be served over HTTPS in production — the CORS and cookie configuration assumes a single canonical https:// origin. Requirements: the ingress host must be under a reachable DNS name, the TLS certificate must match the ingress host (wildcard certs work), and port 443 must be reachable from workstations, not just port 80.

spec:
  tls:
    - hosts:
        - qa-infinity.apps.your-cluster.example.com
      secretName: wildcard-tls-secret   # existing cert secret in the namespace
  rules:
    - host: qa-infinity.apps.your-cluster.example.com
      ...yaml

CORS Configuration (Production)

The API rejects requests from origins not listed in CORS_ORIGIN with 403 Forbidden (not 500). A mismatch causes all browser requests to fail with a CORS error. Set both variables to the exact https:// URL your users access QA Infinity on:

APP_URL=https://qa-infinity.apps.your-cluster.example.com
CORS_ORIGIN=https://qa-infinity.apps.your-cluster.example.com.env
ℹ️
The API logs a startup warning if CORS_ORIGIN is unset or does not include APP_URL. Check docker logs qa-api (or your pod logs) immediately after startup if browser requests fail.

Multiple origins (e.g. staging + production on the same API):

CORS_ORIGIN=https://qa-infinity-staging.example.com,https://qa-infinity.example.com.env

Build & Package

If you have SSH/SCP access to their server, use release mode — it builds, transfers, and starts everything in one shot:

.\deploy.ps1 -Mode release -SSH <new-team-ssh-alias> -RemoteDir /opt/qa-infinity `
             -CorsOrigin http://<their-server-ip>:3100 `
             -StripExtraHostspowershell

If there’s no SSH/network path to their server at all, use package mode instead. It does the exact same build+save, but skips SSH entirely and produces a single zip (image tarballs + config + a generated INSTALL.md guide) that you hand over however you can — email, USB, file share:

.\deploy.ps1 -Mode package -CorsOrigin http://<their-server-ip>:3100 `
             -StripExtraHosts -OutZip C:\handoff\qa-infinity.zippowershell

-StripExtraHosts removes this deployment’s internal-network extra_hosts entries — specific to the current target application and meaningless (and unnecessarily revealing) on the new team’s network. -OutZip is optional; defaults to ..\releases\Fresh Install\qa-infinity-offline-<timestamp>.zip.

⚠️
The zip’s .env carries real secrets from this deployment (DB password, JWT secret) — share it over a secure channel, and tell the receiving team to rotate those values for their own instance rather than reuse them.

📌 TC ID Tagging — Required for Correct Per-Test Reporting

⚠️
Without TC ID tags, all test cases in a .robot file will show FAILED if even one test fails. QA Infinity maps execution results back to individual test cases using the [Tags] field in each Robot Framework test case block. If the tag is missing, the tool has no way to distinguish which test passed and which failed — so it falls back to the file-level exit code and marks every TC in the file as FAILED.

Follow this four-step workflow for any legacy Selenium or Robot Framework script import to ensure individual test case results are reported correctly:

  • 1
    Prepare your master test cases and import them via Excel
    Before importing any scripts, create your test cases in the TC Library using the Import Excel function.

    If your team already has TC IDs in an offline Excel sheet (e.g. TC-AIRTEL-161, TC-AIRTEL-162), include a TC ID column in the Excel file when importing. The tool will retain your existing IDs rather than auto-assigning new ones — so the IDs you have already used in your .robot files' [Tags] will match exactly after import. No renaming needed.

    If no TC ID column is provided, the tool auto-assigns IDs. In that case, note the assigned IDs and update the [Tags] in your .robot files to match before importing the ZIP.

    TC Library → Import → Upload Excel → Map columns (map your TC ID column) → Import
  • 2
    Add the TC ID to [Tags] in each Robot Framework test case
    Open each .robot file and add a [Tags] line containing the matching TC ID inside every *** Test Cases *** block. The TC ID must match exactly (including case) what is shown in the TC Library.

Example — a .robot file with two test cases, each tagged with its TC ID:

*** Test Cases ***
TC06_Deactivate_Parent_With_Active_Child_Blocked
    [Tags]    TC-AIRTEL-161
    Open Browser    ${URL}    chrome
    Login To Application    ${USERNAME}    ${PASSWORD}
    Navigate To Customer Management
    Select Parent Account    PARENT-001
    Click Deactivate
    Verify Error Message    Cannot deactivate: active child accounts exist
    [Teardown]    Close Browser

TC08_Delete_Parent_Designation_With_Child_Blocked
    [Tags]    TC-AIRTEL-162
    Open Browser    ${URL}    chrome
    Login To Application    ${USERNAME}    ${PASSWORD}
    Navigate To Designation Management
    Select Parent Designation    DESIG-001
    Click Delete
    Verify Error Message    Cannot delete: child designations are linked
    [Teardown]    Close Browser.robot
ℹ️
One TC ID per test case block. If a single .robot file contains multiple *** Test Cases *** blocks (a suite file), every block must have its own unique [Tags] TC-AIRTEL-XXX line. The TC ID in [Tags] is how QA Infinity knows which test case result belongs to which TC in the library.
  • 3
    Import the ZIP — the tool maps scripts to TCs automatically
    Once your .robot files have the correct [Tags], zip the project and import it via Scripts → Import Script → Import Folder (ZIP).

    QA Infinity scans every test case block in the uploaded scripts, reads the [Tags] field, and automatically links each test to the matching TC ID in the library. No manual linking needed.

    To verify the mapping was successful: go to the TC Library. Any TC that has been linked to a script will show a 🔗 link icon next to its TC ID. If the link icon is missing, the tag in the .robot file is either absent or does not match the TC ID exactly.
  • 4
    Run — results are reported per test case, not per file
    When you execute the suite, QA Infinity reads the individual PASS / FAIL result for each test case from the RF output.xml and maps it back to the correct TC via its tag. Each TC in the run report shows its own result independently — a failing test in a suite file does not mark all other tests in the file as FAILED.

    Without the tag, the tool can only see the file-level exit code — fail anywhere = fail everywhere.
💡
Quick checklist before importing a legacy script ZIP:
  1. All master TCs imported to the TC Library via Excel — TC IDs assigned ✓
  2. Every *** Test Cases *** block in every .robot file has [Tags] TC-AIRTEL-XXX ✓
  3. TC IDs in [Tags] match exactly what the TC Library shows ✓
  4. After import: TC Library shows 🔗 link icon next to each mapped TC ✓

  • 1

  • 2

  • 3

  • 5

How captured locators improve script generation

Locators saved to the repository are surfaced to the AI script agent as an autocomplete hint pool. When the agent writes a keyword like Click Save Order button, it checks the repository first. If a matching locator exists, it uses the exact captured selector instead of guessing.

💡
Recommended workflow. Before generating scripts for a new feature, spend 5–10 minutes on the Locator Picker — click every button, field, and nav item the feature uses. This one-time investment eliminates most selector failures across all scripts generated for that feature.

You can also view and edit all saved locators on the Locators page in QA Infinity: rename them, correct the selector string, or delete stale entries. Locators are project-scoped — the same repository is used by all TCs in the project.

Flow Recorder — Creating Skills from Live Interactions

The Flow Recorder captures your interactions on the live application step by step and imports them as a UI_FLOW skill. Because the skill was recorded against the real application, it contains verified selectors — the AI treats these as authoritative and copies them verbatim into every generated script that uses the skill.

📺
What the recorder captures:
  • Clicks on buttons, links, icon buttons
  • Text input into form fields (type events)
  • React Select / infinite-select dropdown selections
  • Checkbox and radio toggle interactions
  • Navigation between pages (URL changes recorded as steps)
Locators are resolved in reliability order: data-testid → role+name → stable ID → CSS path.

Use Case 3 — Recording a Complex Form Interaction

For forms with custom dropdowns, date pickers, or multi-step modals, a recorded skill gives the agent the exact interaction sequence. Without it, the agent must guess how to open and select from custom components — which almost always fails.

  2. Fill the form completely: click each field in order, select dropdown values, pick dates, handle any modals.
  3. Stop recording after the form is submitted or after the interaction sequence you want to teach.

🌟 Creating Perfect Test Cases & Scripts

A structured approach to getting accurate, runnable Robot Framework scripts on the first generation — without manual selector hunting. Follow this workflow once per feature and the system compounds from there.

ℹ️
Why this matters. The script agent never sees your live application. Every locator it writes is guesswork — unless you feed it verified, app-specific knowledge through Skills. The more accurate your skills library, the more accurate the generated scripts.

Step 1 — Build Your Skills Library

Skills are the AI’s knowledge base about your application. Set them up once per project/feature. They are automatically injected into every script generation prompt.

🔴
Do this before generating any scripts. A project with no skills will produce guessed locators that will fail. A well-stocked skills library produces scripts that run on first attempt.

1a. Login Skill GLOBAL • Mandatory

The most critical skill. The agent treats any UI_FLOW skill whose name or scope contains “login” as the MANDATORY LOGIN SKILL — it gets injected into every script with the highest-priority instruction banner and the agent is told to copy its locators verbatim.

  • 1
    Go to Skills → + New Skill → Type: UI_FLOW
    Name it exactly “Login” or include “login” in the name. Set Tier: GLOBAL so it injects into all scripts regardless of feature.
  • 2
    Use Capture from Browser to record the login flow
    The system opens a real browser session. Perform the login yourself — click the username field, type credentials, click the submit button, wait for the dashboard. This captures the exact selectors (css=#username, css=#kc-login) with [RECORDED IN LIVE BROWSER] trust flag.
  • 3
    Verify the captured selectors make sense
    Check that the username, password, and submit selectors look correct. Recorded skills get the highest trust — the agent copies them verbatim and will never substitute alternatives.
⚠️
Keycloak / SSO apps. If your app uses an SSO redirect (Keycloak, ADFS, Azure AD), the recorder may capture the SSO URL. The agent is programmed to ignore the raw SSO redirect URL and always navigate to ${BASE_URL} instead — the redirect happens automatically. The important part is capturing the correct username/password field selectors on the SSO page.

1b. Navigation Helper Skills UI_FLOW • FEATURE-scoped

For each feature group (use-case tag), create one navigation helper that records the exact menu path to reach the main page for that feature. This solves the biggest locator problem: sidebar navigation.

Ventas sidebar tip. The Ventas sidebar has two element types: section headers (collapse toggles, use text=Stock Creation) and leaf links (navigable pages, use role=link[name="Stock"]). The agent knows this distinction — but only if it has a recorded skill showing the full click sequence. Never skip recording the section header clicks; the sidebar starts collapsed.

Set the Feature Group on each navigation skill to match the use-case tag of the TCs it supports (e.g. primary-sales). The agent only receives feature-scoped skills when the TC it is generating carries the matching tag — keeping prompts focused and token-efficient.

1c. Business Rules & HLD FUNCTIONAL_RULES • BUSINESS_USE_CASE

Document the business logic the agent must respect when writing assertions and test data. Examples: mandatory fields, valid value ranges, workflow state rules, approval flows.

  • FUNCTIONAL_RULES — rules that govern field validation, form behaviour, workflow transitions (e.g. “GRN cannot be submitted without a PO number”).
  • BUSINESS_USE_CASE — high-level descriptions of what the feature does end-to-end. Helps the agent understand why steps exist, not just what to click.
  • HLD — high-level design documents. Upload as plain text or paste content. The agent uses these to write accurate expected-result assertions.

Set the feature group to scope these skills to the relevant use-case. Keep content factual and terse — the agent reads every word in the prompt window.

1d. Test Data TEST_DATA • FEATURE-scoped

Provide concrete valid values the agent can use in generated scripts. Without this, the agent invents placeholder data that may fail field validation.

If the feature requires testing under a specific role (e.g. “Warehouse Manager” vs “Finance Reviewer”), create a USER_ROLE skill that stores the test credentials for that role. The agent injects TC_USERNAME and TC_PASSWORD directly from this skill into the generated *** Variables *** section.

The Reference Script Strategy

This is the most powerful technique for getting accurate scripts at scale. Instead of only giving the agent instructions, you give it a verified working example — a TC and its passing script together as a skill. The agent mirrors the locators and navigation patterns exactly.

⚠️
The locator problem. Even with Login and Navigation skills, the agent still guesses locators for form fields it has never seen. The only way to give it ground truth for a specific form is to show it a script that already worked against that form — that is what a Reference Script does.

Why it works

When the agent receives a REFERENCE_SCRIPT skill, it sees this in the prompt:

  ```robot

The agent treats this as authoritative ground truth — it copies the same css=#sixdee_field_infinite_select_warehouse, role=link[name="Stock"], and Keyboard Input patterns instead of guessing. For a negative test on the same form, only the test data and assertion step needs to change; all navigation and form-fill locators stay identical.

How to create a Reference Script skill

  • 1
    Pick 2–4 “happy path” TCs for the feature
    Choose TCs that cover the full navigation and the main form interactions for the feature. These become your reference anchors for all other TCs in the same feature group.
  • 2

    Use the Generate Script modal with the Login and Navigation skills pinned. Run the script. If it fails, fix it manually using the editor — update selectors, correct navigation steps.

  • 4
    For the next TC in the same feature: open Generate Script, the reference skill appears in the auto-detected chips
    Since the Reference Script skill has the same Feature Group as the TC’s use-case tag, the modal pre-selects it automatically. The agent receives the full verified example and produces a much more accurate script.

The flywheel. Each passing script you promote becomes a better source of truth for the next generation. After 3–4 reference scripts per feature, the agent has seen every important locator in a verified context — new TCs (negative cases, edge cases, monkey tests) can be generated with near-zero manual correction needed.

⭐ Tips for Best Output

1. Always Set Up a Login Skill First

Before generating any UI test cases, create a Login skill. This is the single biggest factor in getting accurate, runnable scripts on first generation.

2. Use Multiple Input Sources Together

Combine a live screen capture + a Jira story + reference TCs from the same feature. This triangulates the AI’s understanding and produces the most precise, non-duplicated test cases.

3. Name Pages Clearly in Menu Context

Fill in the Page Name field with the exact menu label (e.g. “New Order” not “order page”). The agent clicks matching navigation elements to land on the right page.

4. Use Feature Groups as Style Ref for New Features

When generating TCs for a feature that already has some TCs, add the entire feature group as a Style Ref. The AI matches the existing step structure, avoids duplication, and maintains numbering conventions.

5. Upload the API Spec for API Testing

For API test generation, always upload the OpenAPI/Swagger YAML rather than pasting a cURL. The spec gives the AI request/response schema, error codes, and field validation rules a cURL snippet doesn’t contain.

6. Approve TCs Before Running

Only APPROVED TCs are included in suites and group runs. Review and approve after each generation session before scheduling runs.

7. Keep Seed TCs Minimal but Specific

Write the essential scenario in 3–5 words per step. Overly detailed seeds constrain the AI unnecessarily; overly vague ones produce generic output.

8. Run Healing After Every Release

Schedule a post-release healing run immediately after deploying new application versions. Catching selector breakage early prevents cascading failures in the regression suite.

9. Set Additional Context for Edge Cases

Use the Additional Context field to specify edge cases, boundary conditions, or test data requirements (e.g. “include negative scenarios for invalid phone numbers”).

10. Use Named Environments Consistently

Store all environment credentials in named env configs (Dev/Staging/UAT) rather than typing them ad-hoc. This makes credential rotation easy and scripts shareable across the team.

Common causes: missing POSTGRES_PASSWORD or JWT_SECRET, port already in use on the host, insufficient Docker memory allocation.

API container exits with “DATABASE_URL must be set”

Ensure your .env file is in the project root (same directory as docker-compose.yml) and that POSTGRES_PASSWORD is set.

File upload shows error or 0 KB

Check that the file is under MAX_UPLOAD_BYTES (default 50 MB). Files under 1 MB display their size in KB. If uploads fail silently, check the browser console for network errors.

Live screen capture takes a screenshot of the login page

You need a Login skill. Go to Skills → + New Skill → Login, capture your login flow, then retry.

Generated test cases are too generic

Add more context: include a live screenshot, reference TCs from the same feature, and fill in the Additional Context field with specific requirements.

Robot Framework scripts fail with “ElementNotFound”

Go to the Healing page. Accept the proposed fix to update the selector and re-run. If no heal is proposed, verify the runner can reach the application URL from inside the Docker network.

Style Ref dropdown shows no results

The search queries approved TCs. Make sure you have approved TCs in your library. Search by TC-AIR- prefix or partial title.

❓ Frequently Asked Questions

Can QA Infinity test mobile applications? ▶
The current version focuses on web-based applications. The runner uses Playwright’s Chromium browser with responsive viewport support, so mobile web views can be tested by setting a mobile viewport in the generated scripts. Native mobile app testing (Android/iOS) is not supported.
How are LLM costs managed? Is there a way to estimate cost per generation? ▶
A typical generation session (one screen + one doc + 10 TCs) uses approximately 15,000–40,000 tokens. At Claude Sonnet pricing via OpenRouter (~$3/M input, $15/M output), this is roughly $0.10–$0.40 per session. Monitor usage in your OpenRouter or Anthropic dashboard. To reduce costs, limit input sources per generation and avoid very large documentation uploads.
Can I use a local LLM (Ollama, LM Studio) instead of a cloud API? ▶
Yes. Set LLM_PROVIDER=openrouter and point OPENROUTER_API_KEY to your LiteLLM proxy URL. LiteLLM acts as an OpenRouter-compatible gateway in front of any local model. For best results, use at least a 70B parameter model — smaller models typically produce lower quality test cases.
Do generated scripts work out-of-the-box or do they need manual editing? ▶
Scripts generated from live screen captures (with a Login skill configured) typically run without modification on the first attempt. Scripts generated from docs-only inputs may need selector adjustments. The Healing module handles post-run breakage automatically.
How do I back up my data? ▶
Back up two things: the PostgreSQL volume and the scripts folder. 
# Backup PostgreSQL
docker exec qa-postgres pg_dump -U qauser qa_infinity > backup.sql

# Backup scripts (already on host filesystem)
cp -r ./scripts ./scripts-backup-$(date +%Y%m%d)bash
Can multiple users collaborate on the same project simultaneously? ▶
Yes. Multiple users with different roles can work on the same project at the same time. For large teams, assign one “Admin” per project and use “Super User” for the rest to avoid accidental overwrites.
What is the maximum file size I can upload? ▶
The default maximum is 50 MB per file (MAX_UPLOAD_BYTES=52428800 in .env). For large specs, consider splitting into feature-level documents to reduce LLM token consumption.
Can I schedule test runs to run automatically at night? ▶
Yes. Go to the Scheduler page, create a new schedule, select a suite, and configure the cron expression (e.g. 0 2 * * * for 2 AM daily).
How does the platform avoid generating duplicate test cases? ▶
At generation time, the API checks for semantic similarity against existing approved TCs and removes near-duplicates before returning results. For maximum deduplication, add the relevant feature group as a Style Ref.
Can QA Infinity be deployed behind a reverse proxy (nginx, Traefik)? ▶
Yes. Update CORS_ORIGIN in .env to your public frontend URL. For WebSocket support (live run events), ensure your proxy passes the Upgrade and Connection headers.
