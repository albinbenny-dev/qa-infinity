QA Infinity User Guide

A self-hosted, AI-driven QA automation platform that generates test cases from natural language inputs, auto-writes Robot Framework scripts, runs them in a managed browser cluster, and self-heals broken selectors — all from a single Docker Compose stack.

✍️
AI Test Writer
Generate full test cases from URLs, API specs, Jira stories, PDFs, screenshots, or existing TC patterns.
📜
Script Generation
Automatically produces Robot Framework scripts with locked locators and trace-verified selector hints.
▶️
Managed Execution
Runs scripts in a headless Playwright cluster. Watch live via built-in noVNC browser.
🩹
Self-Healing
Detects broken selectors and proposes AI-generated fixes without re-running the entire suite.
🎯
Skills System
Teach the AI how to log in, navigate menus, and fill forms — reusable across all generated scripts.
💬
AI Chat
Ask questions about your test suite, generate ad-hoc tests, or get explanations via project-aware chat.

✍️ Test Writer

The Test Writer is the primary interface for generating test cases. Add one or more input sources, configure test types, then click Generate.

💡
Combine multiple input sources for richer output. Add a screen URL + a Jira story + a reference TC together. The more context you give, the more accurate and complete the generated test cases.

Screen Input (Live Capture)

Provide a URL and the platform authenticates with stored credentials, navigates to the correct page, and takes an annotated screenshot as visual context.

  • Page Name / Menu Context — tell the agent which page to land on (e.g. “New Order form”). It clicks matching nav items after login.
  • Environment — select a named env config to use its credentials automatically.
  • Upload Screenshot — paste (Ctrl+V) or drag a screenshot to skip live capture entirely.
  • Agentic Trace — enables multi-step browser interaction for complex flows.

API Input

Use the API tab to generate API test cases. Selecting this tab auto-sets Test Types to API + SIT.

Docs Input

Upload requirement documents, HLDs, BRDs, or SIT docs. Supported: PDF, Word (.docx), Excel (.xlsx), plain text, Markdown. Multiple files supported in one go.

Style Ref (Reference TCs)

Reference existing TCs to guide the AI’s writing style and avoid duplication.

  • Individual TC — search by TC-ID (e.g. TC-AIR-042) or title.
  • Feature Group — type a feature name (e.g. “Primary Sales”). All TCs in that group are added. The AI uses them to avoid duplication and maintain consistent phrasing.

Jira Input

Paste a Jira story URL. The agent fetches the title, description, and acceptance criteria to generate AC-aligned test cases. Requires JIRA_HOST, JIRA_EMAIL, and JIRA_API_TOKEN in .env.

Seed TCs

Upload an Excel file with an existing test case outline. The AI enriches each seed with detailed steps, login sequences, and selector hints without changing the core logic.

📋 TC Library

All generated and approved test cases live in the TC Library, organized by use-case group (feature).

  • Approve — moves a DRAFT TC to APPROVED, making it eligible for script generation and test runs.
  • Edit — inline editing of title, steps, expected results, priority, tags, and test data.
  • Duplicate — clones a TC as a starting point for variations.
  • Bulk Approve — select multiple TCs and approve in one click.
  • Bulk Move — reassign TCs to a different use-case group.
  • Search & Filter — filter by type, status, use-case tag, or free-text search.
💡
Use the TC-ID prefix system. TC IDs are auto-assigned (e.g. TC-AIR-001). Reference them in Jira, in chat, and in the Style Ref search to maintain traceability.

🩹 Healing

When scripts fail due to changed UI selectors, Healing automatically detects broken selectors and proposes AI-generated fixes.

How It Works

  1. A script run fails with “Element not found”.
  2. QA Infinity captures failure context (page source, error, step).
  3. The AI analyzes the DOM and proposes alternative locators.
  4. You review the proposed fix — accept or reject.
  5. Accepted fixes are applied to the script file immediately.
💡
Run healing after each application release. Even a small UI change can break selectors. The healing workflow takes minutes and keeps your regression suite green.

🌟 Creating Perfect Test Cases & Scripts

A structured approach to getting accurate, runnable Robot Framework scripts on the first generation — without manual selector hunting. Follow this workflow once per feature and the system compounds from there.

ℹ️
Why this matters. The script agent never sees your live application. Every locator it writes is guesswork — unless you feed it verified, app-specific knowledge through Skills. The more accurate your skills library, the more accurate the generated scripts.

Step 1 — Build Your Skills Library

Skills are the AI’s knowledge base about your application. Set them up once per project/feature. They are automatically injected into every script generation prompt.

🔴
Do this before generating any scripts. A project with no skills will produce guessed locators that will fail. A well-stocked skills library produces scripts that run on first attempt.

1a. Login Skill GLOBAL • Mandatory

The most critical skill. The agent treats any UI_FLOW skill whose name or scope contains “login” as the MANDATORY LOGIN SKILL — it gets injected into every script with the highest-priority instruction banner and the agent is told to copy its locators verbatim.

  • 1
    Go to Skills → + New Skill → Type: UI_FLOW
    Name it exactly “Login” or include “login” in the name. Set Tier: GLOBAL so it injects into all scripts regardless of feature.
  • 2
    Use Capture from Browser to record the login flow
    The system opens a real browser session. Perform the login yourself — click the username field, type credentials, click the submit button, wait for the dashboard. This captures the exact selectors (css=#username, css=#kc-login) with [RECORDED IN LIVE BROWSER] trust flag.
  • 3
    Verify the captured selectors make sense
    Check that the username, password, and submit selectors look correct. Recorded skills get the highest trust — the agent copies them verbatim and will never substitute alternatives.
⚠️
Keycloak / SSO apps. If your app uses an SSO redirect (Keycloak, ADFS, Azure AD), the recorder may capture the SSO URL. The agent is programmed to ignore the raw SSO redirect URL and always navigate to ${BASE_URL} instead — the redirect happens automatically. The important part is capturing the correct username/password field selectors on the SSO page.

1b. Navigation Helper Skills UI_FLOW • FEATURE-scoped

For each feature group (use-case tag), create one navigation helper that records the exact menu path to reach the main page for that feature. This solves the biggest locator problem: sidebar navigation.

💡
Ventas sidebar tip. The Ventas sidebar has two element types: section headers (collapse toggles, use text=Stock Creation) and leaf links (navigable pages, use role=link[name="Stock"]). The agent knows this distinction — but only if it has a recorded skill showing the full click sequence. Never skip recording the section header clicks; the sidebar starts collapsed.
Feature GroupSkill NameWhat to Record
Primary SalesNavigate to New OrderMenu clicks from dashboard to the New Order form
Stock ManagementNavigate to Stock CreationStock Creation → Stock Management → Stock page
ReportsNavigate to ReportsReports menu expansion + sub-menu click

Set the Feature Group on each navigation skill to match the use-case tag of the TCs it supports (e.g. primary-sales). The agent only receives feature-scoped skills when the TC it is generating carries the matching tag — keeping prompts focused and token-efficient.

1c. Business Rules & HLD FUNCTIONAL_RULES • BUSINESS_USE_CASE

Document the business logic the agent must respect when writing assertions and test data. Examples: mandatory fields, valid value ranges, workflow state rules, approval flows.

  • FUNCTIONAL_RULES — rules that govern field validation, form behaviour, workflow transitions (e.g. “GRN cannot be submitted without a PO number”).
  • BUSINESS_USE_CASE — high-level descriptions of what the feature does end-to-end. Helps the agent understand why steps exist, not just what to click.
  • HLD — high-level design documents. Upload as plain text or paste content. The agent uses these to write accurate expected-result assertions.

Set the feature group to scope these skills to the relevant use-case. Keep content factual and terse — the agent reads every word in the prompt window.

1d. Test Data TEST_DATA • FEATURE-scoped

Provide concrete valid values the agent can use in generated scripts. Without this, the agent invents placeholder data that may fail field validation.

# Example TEST_DATA skill content (paste as JSON or plain text)
validData: {
  "poNumber": "PO-2025-00142",
  "grnNumber": "GRN-2025-00087",
  "quantity": "10",
  "warehouse": "Nairobi Central"
}
referenceData: {
  "productCode": "SIM-STANDARD-250",
  "supplierCode": "VENDOR-AIRTEL-01"
}JSON

Values in validData are injected verbatim into the ${TC_USERNAME}/${TC_PASSWORD}-style variables. Values in referenceData supply option codes and look-up IDs for dropdown fields.

1e. User Role USER_ROLE • FEATURE-scoped

If the feature requires testing under a specific role (e.g. “Warehouse Manager” vs “Finance Reviewer”), create a USER_ROLE skill that stores the test credentials for that role. The agent injects TC_USERNAME and TC_PASSWORD directly from this skill into the generated *** Variables *** section.

1f. Locator Guide LOCATOR_GUIDE • GLOBAL

A freeform skill describing the application’s ID and selector patterns. Useful when the app uses a consistent naming convention the agent should follow (e.g. id=sixdee_field_<name> for all form inputs). Set this as GLOBAL — it applies to every script in the project.

# Example LOCATOR_GUIDE content
All form input fields follow the pattern: css=#sixdee_field_<fieldName>
Custom dropdowns use: css=#sixdee_field_infinite_select_<fieldName>
Submit buttons always have: css=button[type="submit"]
Section navigation headers are <a role="button"> — use text= selector, not role=link.
Leaf page links are <a href> — use role=link[name="exact name"] for precise matching.plain text

How Skill Injection Works

The agent does not receive all skills every time. The injection pipeline filters and orders skills before the prompt is built:

TierWhen injectedUse for
GLOBALEvery script generation, regardless of featureLogin skill, Locator Guide, company-wide business rules
FEATUREOnly when TC’s use-case tag matches the skill’s Feature GroupNavigation helpers, feature-specific test data, HLD per module
HISTORICALOnly when TC’s use-case tag matches the skill’s Feature GroupPast corrections, known failure patterns, QA engineer notes
PinnedAlways — explicitly selected in the Generate Script modalReference scripts, ad-hoc overrides for a specific generation run

Pinned skills always come first in the prompt. The agent is told: “Mirror its locators, navigation, and RF syntax EXACTLY.” Auto-detected (tier-based) skills follow, deduplicated by name so the same skill never appears twice.

🤖
What the agent sees per skill type:
  • UI_FLOW (Login) — MANDATORY LOGIN SKILL banner + all recorded locators + annotated Playwright code with RF transformation rules inline
  • UI_FLOW (Navigation) — Target URL + navigation path + locators + step-by-step flow
  • FUNCTIONAL_RULES / HLD — Raw text injected as business context for assertions
  • TEST_DATA — validData and referenceData as concrete values for variables
  • USER_ROLE — TC_USERNAME / TC_PASSWORD values for the role
  • LOCATOR_GUIDE — ID patterns and selector conventions
  • HISTORICAL — QA corrections that must not be repeated
  • REFERENCE_SCRIPT — VERIFIED PASSING EXAMPLE banner + TC snapshot + full verified script body

Step 2 — Use the Generate Script Modal

Open a TC in the Scripts page and click Generate Script. The redesigned modal gives you full control over which skills the agent receives.

  • 1
    Auto-detect pre-fills skills for you
    On open, the modal reads the TC’s use-case tag and automatically selects all skills whose Feature Group matches. GLOBAL skills (Login, Locator Guide) are always included. You will see them appear as chips immediately.
  • 2
    Review the chips — deselect irrelevant skills
    Click the × on any chip to remove it from this generation. Fewer, more relevant skills produce better output than a large noisy set. Remove navigation helpers for features the TC does not visit.
  • 3
    Add skills from the dropdown
    Click the skill selector dropdown to browse all project skills. Add Reference Scripts from related TCs, or add a User Role skill if the TC requires a non-default role.
  • 4
    Click Generate
    The selected skill IDs are passed alongside the TC to the script agent. Pinned skills are injected first, then feature-matched skills are appended (deduped). The agent always generates in Robot Framework mode.
💡
Add context for the specific run. Use the Additional Context field to give the agent one-time instructions (e.g. “this test must cover the negative case where the PO number is already closed”). This is different from skills — it is ephemeral and not stored.

The Reference Script Strategy

This is the most powerful technique for getting accurate scripts at scale. Instead of only giving the agent instructions, you give it a verified working example — a TC and its passing script together as a skill. The agent mirrors the locators and navigation patterns exactly.

⚠️
The locator problem. Even with Login and Navigation skills, the agent still guesses locators for form fields it has never seen. The only way to give it ground truth for a specific form is to show it a script that already worked against that form — that is what a Reference Script does.

Why it works

When the agent receives a REFERENCE_SCRIPT skill, it sees this in the prompt:

╔═══════════════════════════════════════════════════════════════╗
║  REFERENCE SCRIPT — VERIFIED PASSING EXAMPLE                ║
║  Mirror its locators, navigation, and RF syntax EXACTLY.    ║
║  Only modify test data and assertions as needed.             ║
╘═══════════════════════════════════════════════════════════════╛
  TC: [TC-AIR-012] Create GRN from valid PO
  Steps: 1. Navigate to Stock page ... 4. Fill GRN form ...
  Verified Robot Framework script:
  ```robot
  *** Test Cases ***
  ...agent prompt

The agent treats this as authoritative ground truth — it copies the same css=#sixdee_field_infinite_select_warehouse, role=link[name="Stock"], and Keyboard Input patterns instead of guessing. For a negative test on the same form, only the test data and assertion step needs to change; all navigation and form-fill locators stay identical.

How to create a Reference Script skill

  • 1
    Pick 2–4 “happy path” TCs for the feature
    Choose TCs that cover the full navigation and the main form interactions for the feature. These become your reference anchors for all other TCs in the same feature group.
  • 2
    Generate and run the script
    Use the Generate Script modal with the Login and Navigation skills pinned. Run the script. If it fails, fix it manually using the editor — update selectors, correct navigation steps.
  • 3
    When the run passes, click 🔖 Ref Skill in the editor toolbar
    This button appears next to the ★ Golden button when a TC and script are both active. Clicking it opens a confirmation dialog where you name the skill and choose its Feature Group. The current script body + TC snapshot are saved together as a REFERENCE_SCRIPT skill.
  • 4
    For the next TC in the same feature: open Generate Script, the reference skill appears in the auto-detected chips
    Since the Reference Script skill has the same Feature Group as the TC’s use-case tag, the modal pre-selects it automatically. The agent receives the full verified example and produces a much more accurate script.
💡
The flywheel. Each passing script you promote becomes a better source of truth for the next generation. After 3–4 reference scripts per feature, the agent has seen every important locator in a verified context — new TCs (negative cases, edge cases, monkey tests) can be generated with near-zero manual correction needed.

Step 3 — End-to-End Workflow for a New Feature

Follow this sequence when onboarding a new feature group into QA Infinity:

①
Set up GLOBAL skills (do once for the project)
Create a UI_FLOW Login skill (GLOBAL tier) by recording your login flow in a live browser. Create a LOCATOR_GUIDE skill (GLOBAL) describing the application’s selector patterns and component conventions.
②
Set up FEATURE skills for the new feature group
Create a Navigation Helper (UI_FLOW, FEATURE tier, Feature Group = use-case tag) by recording the menu path to the feature’s main page. Add a TEST_DATA skill with valid PO numbers, product codes, warehouse names etc. Add a FUNCTIONAL_RULES skill with field validation rules and workflow constraints.
③
Generate & verify 2–4 happy-path TC scripts
Pick the core happy-path TCs. Open Generate Script, confirm the auto-detected chips (Login + Navigation Helper + Test Data), click Generate. Run each script. Fix any selector issues manually in the Monaco editor. Re-run until green.
④
Promote passing scripts to Reference Script skills
For each passing script, click 🔖 Ref Skill in the editor toolbar. Name it descriptively (e.g. “GRN Create — Happy Path”). Set Feature Group to the same use-case tag. The verified TC + script body is saved as a REFERENCE_SCRIPT skill.
⑤
Generate all remaining TCs (negative, edge, monkey)
For every other TC in the feature group, open Generate Script. The Reference Script skills now appear as pre-selected chips alongside Login and Navigation. The agent mirrors the verified locators — it only needs to change test data and assertion logic. Most scripts will run without any manual correction.

Each new TC in the project benefits from an increasingly accurate set of verified examples. This is the flywheel: passing scripts → Reference Skills → more passing scripts.

⭐ Tips for Best Output

1. Always Set Up a Login Skill First

Before generating any UI test cases, create a Login skill. This is the single biggest factor in getting accurate, runnable scripts on first generation.

2. Use Multiple Input Sources Together

Combine a live screen capture + a Jira story + reference TCs from the same feature. This triangulates the AI’s understanding and produces the most precise, non-duplicated test cases.

3. Name Pages Clearly in Menu Context

Fill in the Page Name field with the exact menu label (e.g. “New Order” not “order page”). The agent clicks matching navigation elements to land on the right page.

4. Use Feature Groups as Style Ref for New Features

When generating TCs for a feature that already has some TCs, add the entire feature group as a Style Ref. The AI matches the existing step structure, avoids duplication, and maintains numbering conventions.

5. Upload the API Spec for API Testing

For API test generation, always upload the OpenAPI/Swagger YAML rather than pasting a cURL. The spec gives the AI request/response schema, error codes, and field validation rules a cURL snippet doesn’t contain.

6. Approve TCs Before Running

Only APPROVED TCs are included in suites and group runs. Review and approve after each generation session before scheduling runs.

7. Keep Seed TCs Minimal but Specific

Write the essential scenario in 3–5 words per step. Overly detailed seeds constrain the AI unnecessarily; overly vague ones produce generic output.

8. Run Healing After Every Release

Schedule a post-release healing run immediately after deploying new application versions. Catching selector breakage early prevents cascading failures in the regression suite.

9. Set Additional Context for Edge Cases

Use the Additional Context field to specify edge cases, boundary conditions, or test data requirements (e.g. “include negative scenarios for invalid phone numbers”).

10. Use Named Environments Consistently

Store all environment credentials in named env configs (Dev/Staging/UAT) rather than typing them ad-hoc. This makes credential rotation easy and scripts shareable across the team.

🔍 Troubleshooting

Container won’t start / stays “unhealthy”

docker compose ps
docker compose logs qa-api --tail 50bash

Common causes: missing POSTGRES_PASSWORD or JWT_SECRET, port already in use on the host, insufficient Docker memory allocation.

API container exits with “DATABASE_URL must be set”

Ensure your .env file is in the project root (same directory as docker-compose.yml) and that POSTGRES_PASSWORD is set.

File upload shows error or 0 KB

Check that the file is under MAX_UPLOAD_BYTES (default 50 MB). Files under 1 MB display their size in KB. If uploads fail silently, check the browser console for network errors.

Live screen capture takes a screenshot of the login page

You need a Login skill. Go to Skills → + New Skill → Login, capture your login flow, then retry.

Generated test cases are too generic

Add more context: include a live screenshot, reference TCs from the same feature, and fill in the Additional Context field with specific requirements.

Robot Framework scripts fail with “ElementNotFound”

Go to the Healing page. Accept the proposed fix to update the selector and re-run. If no heal is proposed, verify the runner can reach the application URL from inside the Docker network.

Style Ref dropdown shows no results

The search queries approved TCs. Make sure you have approved TCs in your library. Search by TC-AIR- prefix or partial title.

Jira integration returns “Unauthorized”

Verify JIRA_EMAIL and JIRA_API_TOKEN in .env. The token must be an API token (not your Jira password) generated at id.atlassian.com. Restart after updating:

docker compose restart qa-apibash

noVNC blank screen at localhost:6180

The runner only starts its VNC server when a test is executing. A blank screen when idle is normal — trigger a test run then check the URL.

docker exec qa-api find /artifacts -mtime +30 -deletebash

# WARNING: deletes ALL data including TCs, scripts, and reports

❓ Frequently Asked Questions

Can QA Infinity test mobile applications? ▶
The current version focuses on web-based applications. The runner uses Playwright’s Chromium browser with responsive viewport support, so mobile web views can be tested by setting a mobile viewport in the generated scripts. Native mobile app testing (Android/iOS) is not supported.
How are LLM costs managed? Is there a way to estimate cost per generation? ▶
A typical generation session (one screen + one doc + 10 TCs) uses approximately 15,000–40,000 tokens. At Claude Sonnet pricing via OpenRouter (~$3/M input, $15/M output), this is roughly $0.10–$0.40 per session. Monitor usage in your OpenRouter or Anthropic dashboard. To reduce costs, limit input sources per generation and avoid very large documentation uploads.
Can I use a local LLM (Ollama, LM Studio) instead of a cloud API? ▶
Yes. Set LLM_PROVIDER=openrouter and point OPENROUTER_API_KEY to your LiteLLM proxy URL. LiteLLM acts as an OpenRouter-compatible gateway in front of any local model. For best results, use at least a 70B parameter model — smaller models typically produce lower quality test cases.
Do generated scripts work out-of-the-box or do they need manual editing? ▶
Scripts generated from live screen captures (with a Login skill configured) typically run without modification on the first attempt. Scripts generated from docs-only inputs may need selector adjustments. The Healing module handles post-run breakage automatically.
How do I back up my data? ▶
Back up two things: the PostgreSQL volume and the scripts folder. 
# Backup PostgreSQL
docker exec qa-postgres pg_dump -U qauser qa_infinity > backup.sql

# Backup scripts (already on host filesystem)
cp -r ./scripts ./scripts-backup-$(date +%Y%m%d)bash
Can multiple users collaborate on the same project simultaneously? ▶
Yes. Multiple users with different roles can work on the same project at the same time. For large teams, assign one “Admin” per project and use “Super User” for the rest to avoid accidental overwrites.
What is the maximum file size I can upload? ▶
The default maximum is 50 MB per file (MAX_UPLOAD_BYTES=52428800 in .env). For large specs, consider splitting into feature-level documents to reduce LLM token consumption.
Can I schedule test runs to run automatically at night? ▶
Yes. Go to the Scheduler page, create a new schedule, select a suite, and configure the cron expression (e.g. 0 2 * * * for 2 AM daily).
How does the platform avoid generating duplicate test cases? ▶
At generation time, the API checks for semantic similarity against existing approved TCs and removes near-duplicates before returning results. For maximum deduplication, add the relevant feature group as a Style Ref.
Can QA Infinity be deployed behind a reverse proxy (nginx, Traefik)? ▶
Yes. Update CORS_ORIGIN in .env to your public frontend URL. For WebSocket support (live run events), ensure your proxy passes the Upgrade and Connection headers.
